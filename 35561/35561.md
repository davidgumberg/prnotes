# [#35561](https://github.com/bitcoin/bitcoin/pull/35561) net: move some CNodeState fields to Peer
_All code comments in `[]` are my own._

## Background

`CNodeState` was introduced in [#3276][pr-3276] as a way of dealing with
validation node state, initially just misbehavior and ban stuff:

```cpp
// Maintain validation-specific state about nodes, protected by cs_main, instead
// by CNode's own locks. This simplifies asynchronous operation, where
// processing of incoming data is done after the ProcessMessage call returns,
// and we're no longer holding the node's locks.
struct CNodeState {
    int nMisbehavior;
    bool fShouldBan;
    std::string name;

    CNodeState() {
        nMisbehavior = 0;
        fShouldBan = false;
    }
};
```

This was to avoid the fact that peer stuff related to validation was defined in
net.h, but only used in main.cpp, and didn't have coherent locking since e.g.
the `getpeerinfo` RPC call from the RPC thread could query nMisbehavior, while a
validation thread was mutating it. To fix this, the validation thread would have
to ask for a lock into a net.h data structure which introduces lock-ordering
which should be avoided when possible ... I think ....

## Problem

Fast forward to today, loads of stuff is locked behind `cs_main` that shouldn't,
this is a performance issue and a deadlock risk.

## Solution

### [net: move cmpctblocks fields from CNodeState to Peer](https://github.com/bitcoin/bitcoin/pull/35561/commits/0954ae669683a3179a362dd47cb6176cda914eb2)

	Both m_requested_hb_cmpctblocks & m_provides_cmpctblocks were
	protected by cs_main which is unnecessary. Instead convert them
	to std::atomic<bool> as Mutex is not needed. This way we don't
	need to worry about potential lock inversion in the future or
	thread safety annotations.

### [net: move fPreferredDownload to Peer, make atomic](https://github.com/bitcoin/bitcoin/pull/35561/commits/765f65971aa4fc6c7c0bdf971b4cdc771a5a296e)

	Also make the m_num_preferred_download_peers counter atomic and add
	an assert in FinalizeNode. The asserts for m_num_preferred_download_peers
	in FinalizeNode are still safe even without cs_main locking because of
	the implicit guarantee that ProcessMessage may not run for a peer
	at the same time as FinalizeNode. This has the nice benefit of being
	able to remove cs_main usage in some places.
